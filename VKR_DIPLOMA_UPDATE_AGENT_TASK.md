## Уточнить train/validation/test split

### CWRU

В задаче классификации CWRU используется:

```text
train / validation / test = 70% / 15% / 15%
```

Это стратифицированное разбиение окон сигнала через `train_test_split` в `src/classification/train.py`, а не file-grouped split.

Готовый текст:

> Для задачи классификации CWRU использовалось стратифицированное разбиение окон сигнала в пропорции 70/15/15. Такое разбиение сохраняет баланс классов, однако не является file-grouped split, поэтому окна одного исходного `.mat`-файла могут попасть в разные подвыборки. Данный факт учитывается как ограничение стендового протокола.

### XJTU-SY

Для основных RUL-семейств `v3_rnn`, `v4_tcn`, `v5_odd` split выполняется по полным run-to-failure траекториям подшипников:

| Split | Подшипники |
|---|---|
| Train | `Bearing1_1`, `Bearing1_2`, `Bearing1_4`, `Bearing2_1`, `Bearing2_2`, `Bearing2_4`, `Bearing3_1`, `Bearing3_2`, `Bearing3_4` |
| Validation | `Bearing1_5`, `Bearing2_5`, `Bearing3_5` |
| Test | `Bearing1_3`, `Bearing2_3`, `Bearing3_3` |

По числу bearing-директорий это 9/3/3, то есть приблизительно 60/20/20, но проценты не следует считать строгими, потому что траектории имеют разную длину.

Готовый текст:

> Разбиение XJTU-SY выполнялось по полным run-to-failure траекториям подшипников. В обучающую выборку включались подшипники с суффиксами 1, 2 и 4, в валидационную — с суффиксом 5, в тестовую — с суффиксом 3. Такое разбиение исключает попадание окон одной деградационной траектории одновременно в train и test.

Важный нюанс по stride:

- базовая конфигурация в коде: `seq_stride=2`, `val_test_stride=1`;
- профиль `balanced` в train-скриптах задаёт `seq_stride=5`, `val_test_stride=2`;
- финальные checkpoint имеют суффикс `profilebalanced_trials...`, поэтому перед точным упоминанием stride в тексте нужно сверить фактический MLflow/checkpoint metadata.

Если агент не проверяет metadata, лучше не писать конкретный stride в дипломе, а ограничиться bearing-level split.
